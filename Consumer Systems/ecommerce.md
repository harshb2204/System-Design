# Designing e-commerce product listing

For a small shop (100 items) design a system through which
The shop owner can:

1. add a new product
2. update/delete existing product
3. list all the products on the website
4. customers should be able to quickly access the catalog

*Payment is out of scope for this problem statement*

## Storage

100 x 1KB ≈ 100 KB data

- not huge data, only 100 rows -> fits on single node
- there seems to be a structure
- we can go ahead with SQL DB <- 'products' table to hold all the catalog

## Serving the data

- simple REST based HTTP webserver is fine
- we will need many (handle large request)
- hence put a load balancer

Load Balancer will have DNS like api.mystore.com

#### Current Architecture
![](/diagrams/catalogarchitecture.png)

End user will interact with the frontend, and frontend will talk to the Load Balancer
The Load Balancer will then forward the request to one of the many API servers
Which in turn talks to SQL DB
![](/diagrams/catalogarchitecture1.png)

## Shop owner's admin interface

Shop owner needs Admin console to manage the catalog.
We can keep the Admin UI separate frontend service
which interacts with the same Backend service to do admin things.
![](/diagrams/catalogarchitecture2.png)

*Note: in real world, early stage startups would do all this in one service.*


## Scaling DB

When a lot of load comes in, the DB will be under heavy load.
Given the use case is to list the pages
the load is certainly **Read Load**, hence we add **Read Replica**
![](/diagrams/catalogarchitecture3.png)
Not a rule that master should only take care of write requests. As the master is only generated by the admin here the writes would be less.
